# Общее описание

- Файловый менеджер Magistratum. Проект-эксперимент выполнен для проверки проектировочных гипотез: модульного монолита, выполненного в функционально-процедурном стиле, и тренировки работы с ИИ для написания кода.

## Архитектура «Модульный монолит»

Основная цель — объединить всё, что касается одного функционала, в одном месте (контроллеры, бизнес-логику, работу с данными). Подход имеет преимущество перед классической сервис-ориентированной структурой: поиск в дереве проекта нужного кода становится короче; дерево проекта меньше раскрыто, так как работа происходит в рамках одного пакета/модуля; перенос пакетов или модулей в другие проекты или на другие фреймворки становится проще, так как всё сгруппировано в одном месте.

## Функциональное ядро, императивная оболочка

Императивным называют код, который напрямую, посредством прямых команд описывает, как выполнить задачу. Как правило, такой способ описания задачи используется в процедурах, то есть они сами уже являются списком действий для достижения результата.

Декларативным называют код, который описывает то, что будет выполнено или какой результат будет возвращён при вызове действия. Ключевое отличие — делегирование выполнения: императивный код контролирует программист, декларативный он просто вызывает.

Код любого проекта можно поделить на две большие категории: бизнес-логику — неповторимую часть конкретного проекта, в которой описываются уникальные, присущие только этому проекту правила и расчеты, и инфраструктурный — общий, часто повторяемый код работы с окружающей приложение средой.

Инфраструктурный код чаще всего является последовательностью шагов, в которой для выполнения следующего шага не обязательно знать результат предыдущего (процедура), а не цепочкой изменения данных, поэтому выражается в императивном стиле. В общем смысле императивный код можно представить как нумерованный список:

1. Шаг один
2. Шаг два
3. Шаг три

Бизнес-логика является последовательной трансформацией данных из одного состояния в другое (учитывая влияние правил, то есть валидаций и условий). Выражается в декларативном стиле, потому что может выглядеть как единая последовательность действий, так как для следующего шага важен результат предыдущего. В общем смысле декларативный код можно представить как связный список:

`входные данные --> шаг один --> шаг два --> шаг три -> результат`

## Неизменяемость

В качестве инструмента контроля трансформаций данных была выбрана неизменяемость: это значит, что любая модификация данных приведёт к созданию нового объекта и новой переменной для его хранения. Такой подход дает несколько преимуществ:

1. **Очевидность.** При каждом изменении нужно присваивать значение переменной, следовательно становится понятно, что функция, получив структуру в аргументах, будет её менять, нет недосказанности.

```python
user = mk_user("test")
user = rename(user, "new name")
```

2. **Транзакции.** По необходимости возможно сохранить предыдущее состояние структуры: достаточно создать новую переменную и присвоить ей значение после изменения.

```python
user = mk_user("test")
new_user = rename(user, "new name")
```

3. **Единая точка валидации.** Каждая изменяющая функция создаёт новый экземпляр объекта, используя конструктор, который содержит все правила валидации.

## Функции вместо объектов

Цепочка действий может использовать любую функцию, которая получает и возвращает данные нужного типа (в последнем случае можно написать функцию-«соединитель»), в отличие от объекта, который может использовать только привязанные к нему функции. Такой подход расширяет возможность построения логики без необходимости заботиться о том, какому объекту принадлежит функция.

## Полиморфизм

Автор уверен, что интерфейсы (контракты) не являются необходимостью для написания заменяемого кода. Учитывая функциональный стиль, для использования функции с полиморфными данными можно использовать другие инструменты: union, перегрузка (если есть поддержка). Для использования полиморфного модуля можно реализовывать в новом модуле все необходимые функции и данные, после чего достаточно просто подменить имя модуля, и он будет импортирован на место старого. Контракты могут быть полезны в одном случае — если у разработчика нет доступа к исходному коду, чтобы посмотреть необходимый набор функций для внедрения.

## Тесты

Проект использует юнит-тесты, которые находятся в модуле, и функциональные тесты — в `backend/tests/`. Тестирование направлено на то, чтобы обеспечить безопасность дальнейшей разработки: при каждом изменении можно запустить их и убедиться, что приложение работает штатно.

## Установка

Требования: Docker и Docker Compose.

1. Скопировать `.env.example` в `.env` и заполнить значения (`MYSQL_*`, `REDIS_PASSWORD`, порты).

2. Запустить проект:

```bash
make run
```

3. Инициализировать базу данных и создать root-пользователя:

```bash
make setup
```

> ⚠️ `setup.py` дропает и пересоздаёт все таблицы — данные будут стёрты.

4. Открыть приложение:

- Backend API: http://localhost:8800 (Swagger: `/docs`)
- Frontend: http://localhost:8840
- Adminer (БД): http://localhost:8820

Вход: `root` / `root`.

Полезные команды:

```bash
make lint             # mypy --strict
make format           # black
make test             # unit-тесты
make functional-test  # функциональные тесты (нужен запущенный стек и make setup)
make apply-migrations # alembic upgrade head
```
